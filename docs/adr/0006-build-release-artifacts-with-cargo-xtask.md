# ADR-0006: build-release-artifacts-with-cargo-xtask

- ステータス: 採用
- 日付: 2026-10-26

## 背景

Phase 6で、配布物(`NightFreewaySS.scr`・配布用zip・SHA-256チェックサム)を、ローカルでもリリース用ワークフローでも同じ手順で作る必要がある。これまでは、実行ファイル`freeway-scr.exe`を手作業で改名し、ワークフローのPowerShellでzip化していた。アイコン(`.ico`)もプログラムで生成してリポジトリに含める。

## 決定

ワークスペースに`xtask`クレートを置き、`.cargo/config.toml`のエイリアスで`cargo xtask <command>`として実行する。ユーザー(2026-10-26)の決定による。

- `cargo xtask dist [--target <triple>]`: リリースビルド、`.scr`へのコピー、zip化、チェックサムの記録を行う。x64とARM64を指定できる。ビルドはWindows上でのみ行う
- `cargo xtask icon`: アイコンを生成する
- `xtask`は外部の依存を持たない。zip(無圧縮の格納のみ)、SHA-256、CRC-32、PNGの書き出し(無圧縮のdeflateブロック)を標準ライブラリで自前実装する。zipの日時は固定(1980-01-01)にして、同じ入力から同じzipとチェックサムが得られるようにする
- 自前実装は、zipを読み戻す検証、公知のテストベクトル、Pythonの`zipfile`と`sha256sum -c`との照合で確かめる

検討した選択肢と選ばなかった理由:

- ワークフロー(PowerShell)だけで作る: ローカルのビルドと手順が分かれ、ローカルの手作業が残る
- `zip`・`sha2`などのクレートを使う: 実装は減るが、リリースを作る処理に依存が増える(サプライチェーンのリスク)。無圧縮のzipなら自前実装が小さく済む
- シェルスクリプト・`just`などの外部ツール: 開発者に追加のインストールを求める

## 結果

- メリット: ローカルとリリースで同じコマンドを使う。依存が増えない。OSに依存しない部分はLinuxでもテストできる
- デメリット・受け入れたトレードオフ: zipが圧縮されないため、配布物が実行ファイルとアイコンの分だけ大きい(アイコンは約0.3 MB)。zip・SHA-256の実装を自分たちで保守する。ターゲットディレクトリは`CARGO_TARGET_DIR`または`target/`のみに対応する
- 将来の見直し条件: 圧縮が必要になった場合、またはzip・SHA-256の処理が複雑になった場合(信頼できるクレートの採用を再検討する)
